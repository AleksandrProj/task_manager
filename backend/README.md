# Task Manager — backend

REST API таск-менеджера для тестового задания. Позволяет создавать задачи,
назначать исполнителей, менять статус и добавлять комментарии.
Вход выполняется через JWT, для управления пользователями доступна Django admin.

## Стек

Python 3.13+, Django, Django REST Framework, PostgreSQL 17, SimpleJWT,
drf-spectacular, Pytest и Ruff. Зависимости устанавливаются через uv;
точные версии зафиксированы в [uv.lock](uv.lock).

## Требования

- Для запуска в Docker: Docker с Compose v2 и Make.
- Для локального запуска: дополнительно Python 3.13+ и uv.
  PostgreSQL можно оставить в Docker или использовать свою.

Команды ниже выполняются из каталога `backend`. Из корня репозитория перейдите
в него командой:

```sh
cd backend
```

## Быстрый старт в Docker

Создайте файл настроек:

```sh
make env
```

Откройте `.env` и замените `DJANGO_SECRET` на собственную случайную строку.
Остальные значения из примера подходят для локальной разработки.
`make env` не перезаписывает существующий файл. Затем запустите приложение:

```sh
make up
```

PostgreSQL запускается первой. После проверки её готовности Django автоматически
применяет миграции и запускает сервер. Чтобы создать первую учётную запись:

```sh
docker compose --env-file .env -f ../docker/docker-compose.yml exec web python manage.py createsuperuser
```

После запуска доступны:

- [Swagger — документация и проверка API](http://localhost:8000/api/schema/swagger-ui/).
- [OpenAPI — схема API](http://localhost:8000/api/schema/).
- [Django admin — управление пользователями и данными](http://localhost:8000/admin/).

Адреса указаны для порта `8000`. Если меняете `APP_PORT`, замените порт в адресах.

## Локальный запуск

После создания и заполнения `.env`:

```sh
uv sync --locked
make db
make run
```

`make db` запускает PostgreSQL в Docker и ждёт её готовности.
`make run` применяет миграции и запускает Django локально.
Если PostgreSQL уже запущена отдельно, укажите её реквизиты в `.env`
и пропустите `make db`.

Создать администратора можно в другом терминале из каталога `backend`:

```sh
uv run python manage.py createsuperuser
```

Если порт уже занят web-контейнером, используйте другой:

```sh
APP_PORT=8001 make run
```

## Настройки окружения

Образец настроек — [.env.example](.env.example). Секреты хранятся в `.env`,
который исключён из Git. Переменные окружения процесса имеют приоритет над файлом.

| Переменная | Назначение | Значение в примере |
| --- | --- | --- |
| `DJANGO_SECRET` | Секрет Django; замените перед запуском | Заглушка |
| `DEBUG` | Режим отладки | `True` |
| `ALLOWED_HOSTS` | Разрешённые хосты через запятую, без протокола и порта | `localhost,127.0.0.1,[::1]` |
| `APP_PORT` | Порт приложения на компьютере | `8000` |
| `DB_HOST` | Адрес БД для локального запуска | `127.0.0.1` |
| `DB_PORT` | Порт БД на компьютере | `5432` |
| `DB_NAME` | Имя базы | `task_manager` |
| `DB_USER` | Пользователь БД | `root` |
| `DB_PASSWORD` | Пароль БД | `root` |

В Docker адрес БД автоматически заменяется на `postgres:5432`.
Если `DEBUG` не задан, отладка выключена. Секрет `DJANGO_SECRET` обязателен.
Подробности, включая генерацию секрета, — в [инструкции запуска](RUNNING.md).

## Авторизация и первый запрос

Публичной регистрации нет. Создайте администратора командой выше,
а обычных пользователей — через Django admin.

1. Откройте Swagger и выполните `POST /api/auth/token/` со своими `username`
   и `password`.
2. Скопируйте `access` из ответа. Нажмите **Authorize** и вставьте его
   в поле `jwtAuth` без префикса `Bearer`.
3. Выполните `POST /api/tasks/` с телом `{"title": "Моя первая задача"}`.
4. Выполните `GET /api/tasks/`, чтобы увидеть созданную задачу.

В других API-клиентах передавайте заголовок:

```http
Authorization: Bearer <access_token>
```

Access действует 15 минут, refresh — сутки. Для нового access отправьте
`{"refresh": "<refresh_token>"}` на `POST /api/auth/token/refresh/`.
Refresh при этом не заменяется. После его истечения нужно войти заново.

## API и права доступа

| Метод | Маршрут | Действие |
| --- | --- | --- |
| POST | `/api/auth/token/` | Получить access и refresh |
| POST | `/api/auth/token/refresh/` | Обновить access |
| GET | `/api/users/` | Список активных пользователей |
| GET | `/api/users/me/` | Свой профиль |
| GET, POST | `/api/tasks/` | Список и создание задач |
| GET, PUT, DELETE | `/api/tasks/{id}/` | Просмотр, изменение и удаление задачи |
| PUT | `/api/tasks/{id}/status/` | Изменение только статуса |
| GET, POST | `/api/comments/` | Список своих комментариев и создание |
| PUT, DELETE | `/api/comments/{id}/` | Изменение и удаление своего комментария |

Все операции с задачами, комментариями и пользователями требуют входа.
Задачи видны создателю и текущему исполнителю. Редактировать и удалять задачу
может только создатель. Исполнитель меняет статус через отдельный маршрут,
например с телом `{"status": "done"}`; другие поля в нём запрещены.
Создателя задачи нельзя назначить её исполнителем.

Статусы: `new`, `in_progress`, `done`. Приоритеты: `low`, `medium`, `high`.
Для создания и обычного редактирования задачи обязателен `title`.
Для комментария обязательны `text` и `task` — ID задачи.
Автор и даты назначаются сервером.

Список комментариев содержит только комментарии текущего пользователя.
Задачи и пользователи выдаются по 20 на страницу, комментарии — по 10.
Следующая страница запрашивается через `?page=2`.
Метод `PATCH` и просмотр отдельного комментария через `GET` не поддерживаются.

Схемы, примеры и ошибки доступны в Swagger. Дополнительные описания:
[задачи и комментарии](tasks/API.md), [пользователи и JWT](users/API.md).

## Тесты и проверка кода

Для локальных проверок установите зависимости через `uv sync --locked`
и запустите PostgreSQL. Затем выполните:

```sh
make test
uv run ruff check .
uv run ruff format --check .
uv run python manage.py check
uv run python manage.py makemigrations --check --dry-run
```

Запуск отдельного набора тестов:

```sh
make test TEST_ARGS="tests/tasks/test_views/test_task_status.py -v"
```

Тесты создают отдельную тестовую БД; пользователю PostgreSQL нужно право
на её создание. Адрес по умолчанию — `127.0.0.1`, порт берётся из `.env`.
Другой адрес передаётся через `make test TEST_DB_HOST=адрес_базы`.

При работе только в Docker тесты можно запустить в web-контейнере:

```sh
docker compose --env-file .env -f ../docker/docker-compose.yml exec web pytest -q
```

## Управление запуском и частые проблемы

| Команда | Назначение |
| --- | --- |
| `make logs` | Смотреть логи контейнеров |
| `make restart` | Пересобрать и пересоздать контейнеры после изменения настроек |
| `make down` | Остановить контейнеры, сохранив данные БД |

- **Порт занят:** измените `APP_PORT` или `DB_PORT` в `.env`.
- **Ошибка подключения к БД:** проверьте её готовность и реквизиты. Данные
  сохраняются в `docker/data/postgres`; смена пароля в `.env` не меняет пароль
  пользователя в уже созданной БД.
- **Ошибка `DisallowedHost`:** добавьте используемый хост в `ALLOWED_HOSTS`
  и перезапустите приложение.

Приведённые команды предназначены для разработки и демонстрации.
Они используют `runserver`; production-запуск отдельно не настроен.
При `DEBUG=False` этот сервер не отдаёт статику админки автоматически.
